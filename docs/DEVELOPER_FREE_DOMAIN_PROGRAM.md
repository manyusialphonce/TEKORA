# TEKORA — Developer Free Domain & Preview Environment Program

**Requirement status:** USER-REQUESTED CAPABILITY / PROPOSED DESIGN  
**Scope:** Long-term platform capability; MVP inclusion to be scored and explicitly approved.  
**Implementation status:** NOT STARTED.  
**Preservation:** Additive only. This document does not replace or reduce any existing domain, DNS, hosting, developer hub, deployment, security, or service-catalogue requirement.

## 1. Product intent

TEKORA should lower the barrier for junior developers, students, self-taught developers, freelancers, bootcamp participants, open-source contributors and early-stage builders who need a real hostname to test, preview, demonstrate or share their websites and development projects without immediately paying for a registrable domain.

The program should provide free, TEKORA-managed **subdomains** and optionally connect them to a safe preview/deployment target. It must clearly distinguish:
- a free subdomain delegated beneath a domain controlled by TEKORA;
- a separately registered custom domain (which is not free by default);
- free DNS/hostname service;
- free hosting/build/runtime (a separate product with separate limits and cost);
- temporary preview URLs generated by deployment providers.

A free hostname does not imply free compute, database, email, storage, bandwidth, uptime SLA, production support or custom-domain registration.

## 2. Naming and domain strategy

Illustrative examples only; no domain below is asserted to be owned, registered, available or approved:
- `username.<TEKORA-managed-lab-domain>`
- `project.<TEKORA-managed-lab-domain>`
- `portfolio.<TEKORA-managed-lab-domain>`
- `api-demo.<TEKORA-managed-lab-domain>`

Do not publish or promise a suffix until TEKORA has verified ownership, registrar/registry terms, DNS control, renewal, trademark/brand suitability and operational funding.

**Recommended security architecture:** use a dedicated registrable domain (separate from the primary customer portal, staff, authentication and email domain) for untrusted customer-hosted previews and user content. This reduces shared browser trust and cookie blast radius. If this is not feasible, use a carefully isolated subdomain boundary, host-only cookies, no parent-domain session cookies, strict CORS/CSP allowlists and no wildcard trust in OAuth redirect URIs. Security review must approve the final suffix.

Wildcard DNS may simplify routing but must not mean every arbitrary hostname is accepted. The edge/reverse proxy must validate a provisioned hostname against an active hostname registry and reject unknown, suspended, expired or unowned labels. Cloudflare documents wildcard DNS behaviour and certificate coverage limitations; certificate coverage must be tested for the exact chosen domain depth and proxy mode.

## 3. Target audiences and supported use cases

- Beginner/junior developers testing HTML, CSS, JavaScript and frontend frameworks.
- Students completing coursework, portfolios and capstone projects.
- Developers testing backend APIs and webhook callbacks.
- Freelancers demonstrating a draft to a client before handover.
- Hackathon, bootcamp and community projects.
- Open-source maintainers sharing demos and documentation.
- Small teams previewing development/staging builds.

Use cases: portfolio preview; static site; temporary project demo; staging website; API endpoint test; webhook receiver; frontend-to-backend integration; proof-of-concept; classroom project. Production-critical workloads and regulated/sensitive data are not the target of the free tier.

## 4. Product capabilities

### 4.1 Free hostname lifecycle
1. User signs up and verifies account/email; add stronger verification/risk checks when signals require it.
2. User selects a permitted label and suffix.
3. System validates syntax, reserved names, profanity/impersonation, collisions, policy and risk.
4. User accepts acceptable-use, privacy, retention and free-tier terms.
5. System reserves label atomically and binds it to the verified user/project.
6. DNS and edge routing are provisioned idempotently.
7. TLS certificate issuance/coverage is verified before marking HTTPS ready.
8. User sees hostname, DNS status, TLS status, target configuration and instructions.
9. User may connect a supported deployment provider or configure a supported target.
10. System monitors ownership, expiry, abuse signals, DNS health and dangling targets.
11. User may renew/extend while eligible, transfer ownership only through verified workflow, or delete.
12. On expiry/suspension/deletion, remove routing safely, revoke target association, clean DNS/cert references as appropriate, preserve audit evidence and apply a documented quarantine before label reuse.

### 4.2 DNS controls
Initial candidate record types: A, AAAA, CNAME and TXT, subject to platform safety policy. MX, NS delegation, CAA, SRV, wildcard and arbitrary advanced records should be disabled by default or require a separately reviewed capability. Prevent users from altering platform-critical records, verification records, certificate records or records belonging to another tenant. Enforce record count, TTL, target, zone and change-rate quotas. Validate CNAME conflicts and DNS standards.

### 4.3 Deployment and integration
- Connect a Git repository or supported deployment provider only with explicit OAuth scopes and consent.
- Support manual target setup for approved hosting providers.
- Provide copyable DNS instructions and verification status.
- Webhook-based deployment status must be authenticated, signed where supported, replay-protected and idempotent.
- Do not store deployment secrets in plaintext or expose them in logs.
- Distinguish hostname allocation from build/deploy/hosting status.
- Do not claim a one-click integration until provider API, plan limits, terms and sandbox have been verified.

### 4.4 TLS and browser security
- HTTPS is mandatory before public preview activation; HTTP may redirect to HTTPS only where safe.
- Automate certificate issuance and renewal, monitor expiry and show certificate state.
- Verify wildcard versus per-host certificate behaviour for the actual domain depth.
- Do not assume wildcard certificates cover arbitrary nested hostnames.
- Use strict hostname routing and prevent Host-header confusion.
- Isolate user content from the TEKORA account portal and staff origin.
- Never scope authentication cookies to the shared parent domain for untrusted hosted content.
- Use exact CORS origins, exact OAuth redirect URIs and restrictive CSP; do not trust every subdomain.
- Apply security headers, upload/content controls, malware/phishing detection and safe error pages.
- Ensure preview sites cannot access internal metadata endpoints, cloud credentials, control-plane networks or other tenants.

## 5. Proposed free-tier policy (not yet approved)

The following are discovery defaults for cost and abuse modelling, not a final commercial promise:
- One free hostname per verified individual account at launch; consider up to three only after capacity/abuse data.
- One active project/target per hostname.
- Renewable 90-day allocation while the account remains active and compliant; renewal reminders before expiry.
- Basic DNS records and automated HTTPS included.
- No email mailbox, outbound email sending, guaranteed uptime/SLA, dedicated IP, wildcard DNS, arbitrary nameserver delegation, premium support or production guarantee.
- No included compute/storage/database unless separately specified by a free compute SKU.
- Reasonable bandwidth/request limits enforced at edge; publish exact limits only after cost and provider validation.
- Inactive/abandoned hostname cleanup after notice and grace period; never reclaim without notice and policy-compliant lifecycle.
- Paid upgrades may add custom domains, advanced DNS, deployment capacity, longer retention, higher quotas and support, without making the free offer deceptive.

Do not implement hardcoded quotas until cost modelling, provider limits and product approval are complete. The pricing engine must represent free price as a versioned zero-price offer with explicit eligibility, quota, expiry, renewal and cost-centre allocation—not as an untracked exception.

## 6. Eligibility, trust and abuse prevention

Eligibility should be inclusive and low-friction while protecting the shared domain reputation:
- verified account and email;
- account age/risk signals and rate limits;
- label and content policy acceptance;
- optional project/repository/portfolio context for elevated quotas;
- stronger verification or manual review for suspicious activity;
- organization/school/bootcamp cohorts can receive controlled allocations through an approved program.

Prohibited or restricted activity includes phishing, credential harvesting, malware, command-and-control, spam, unsolicited bulk messaging, impersonation, copyright infringement, illegal content, scams, botnets, cryptomining, open proxies, malicious redirects, credential stuffing and attempts to evade suspension. Maintain a clear reporting and appeal process.

Controls:
- per-account, per-IP/network, per-device and per-project issuance/rate limits with privacy/legal review;
- reserved labels for system names, brands, government, financial institutions and high-risk terms;
- detection of lookalike/typosquatting and impersonation;
- automated abuse signals plus human review for consequential action;
- customer report/takedown channel and abuse contact;
- suspend hostname or routing quickly when credible harm is identified;
- preserve minimal evidence under documented retention/legal process;
- false-positive appeal, restoration and audit trail;
- prevent free-account churn and repeated label cycling;
- never expose one customer's account identity or private details to another customer.

## 7. Resource and state model

Suggested entities (logical, not final schema):
- FreeDomainProgram / ProgramVersion
- HostnameReservation
- ManagedHostname
- HostnameOwnershipVerification
- DNSZone / DNSRecord / DNSChange
- HostnameTargetBinding
- DeploymentConnection
- CertificateBinding / CertificateStatus
- FreeTierEntitlement / QuotaSnapshot
- AbuseSignal / AbuseCase / Appeal
- HostnameLifecycleEvent / AuditEvent

Suggested hostname states:
REQUESTED → VALIDATING → RESERVED → DNS_PENDING → TLS_PENDING → READY → ACTIVE.
Exceptions/transitions: REJECTED, CONFIGURATION_ERROR, UNKNOWN, SUSPENDED, EXPIRY_WARNING, EXPIRED, DELETION_PENDING, QUARANTINED, RELEASED, MANUAL_REVIEW.

Invariants:
- unique active hostname label within suffix;
- tenant/project ownership checked on every read/write;
- DNS changes have idempotency keys and audit events;
- never activate before DNS routing and HTTPS are verified;
- never reassign while stale DNS, target association, certificate or cache state can serve prior content;
- expiry and suspension are separate from deletion;
- label reuse only after quarantine and takeover checks;
- provider timeout is UNKNOWN pending reconciliation, not assumed failure;
- all quota changes and operator overrides are audited.

2. Choose hostname: label input, live availability, suffix selector only where approved, reserved-name explanation.

## 10. Operational, cost and reliability requirements

- Forecast per-hostname DNS, proxy, TLS, bandwidth, request, WAF, support and abuse-review costs.
- Establish cost ceilings, per-account quotas, global kill switch and emergency hostname suspension.
- Monitor DNS propagation, certificate issuance/renewal, origin health, error rates, latency, bandwidth, abuse reports, allocation/expiry and orphaned targets.
- Maintain DNS inventory linked to owner, project, target, creation/expiry and reason.
- Detect dangling CNAME/A/NS targets and stale deployment bindings.
- Use controlled decommissioning: detach target, remove/update DNS, wait appropriate TTL, verify no takeover, revoke certificates/associations as appropriate, update inventory and only then release label after quarantine.
- Maintain runbooks for certificate failure, DNS misconfiguration, abuse incident, provider outage, stale target, accidental deletion and restoration.
- Keep platform status separate from target-provider health and any SLA.

## 11. Testing and acceptance criteria

Required test groups:
- label syntax, IDN/punycode policy, reserved names, collisions and concurrent reservation race;
- tenant isolation and cross-account hostname enumeration;
- unauthorized DNS record types/targets, TTL and quota bypass;
- DNS propagation and provider timeout/reconciliation;
- TLS issuance, renewal, wildcard-depth mismatch and certificate expiry;
- Host-header routing, unknown hostname rejection and origin isolation;
- CORS, CSP, cookie scope and OAuth redirect exact-match;
- malicious content, phishing report, suspension, false positive and appeal;
- expiry reminders, renewal, grace, quarantine and safe reuse;
- stale CNAME/A/NS, dangling target and subdomain takeover simulation in an authorized test zone;
- deployment OAuth scope, secret masking, webhook signature/replay and provider outage;
- billing/free-entitlement quota, cost ceiling, rate limit and global kill switch;
- accessibility, responsive UX and Swahili/English copy.

Minimum acceptance:
1. An eligible verified developer can reserve an available hostname without payment.
2. Duplicate/concurrent requests cannot allocate the same hostname twice.
3. Hostname does not become READY until DNS and valid HTTPS are verified.
4. A user cannot view, modify, renew, transfer or delete another tenant's hostname.
5. Unsupported DNS records and unsafe targets are rejected with actionable errors.
6. Unknown/unallocated hostnames do not route to arbitrary user content.
7. Free-tier limits and expiry are visible and enforced server-side.
8. Suspension/deletion removes routing and prevents stale-target takeover.
9. Abuse reporting, evidence, review, appeal and audit paths work.
10. All operations are observable, recoverable, documented and covered by automated tests.

## 12. Dependencies and unresolved decisions

- Decide whether to use a dedicated registrable domain for user-hosted content.

- Validate edge/reverse proxy, TLS issuance/renewal and certificate depth for the selected hostname model.
- Decide whether first release offers DNS-only hostnames or also deployment/preview hosting.
- Define acceptable-use policy, takedown/appeal process, privacy, retention and legal review.
- Model unit costs and approve quotas, expiry, renewal and abuse budget.
- Decide individual versus school/bootcamp cohort allocation.
